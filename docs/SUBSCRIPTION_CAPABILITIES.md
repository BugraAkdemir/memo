# Subscription model capabilities

Memo matches models returned by the signed-in CLIProxyAPI sidecar with the upstream [published registry](https://raw.githubusercontent.com/router-for-me/CLIProxyAPI/main/internal/registry/models/models.json). It reads exact model IDs, `context_length` and `thinking.levels`; it does not infer subscription capacities from model-family names or invent effort labels. Catalog entries never add models to the account list or the chat picker.

`data/cliproxy/model-capabilities.json` (resolved with `config.DataPath`) stores the last successful capability snapshot. The cache refreshes after six hours, serves stale data immediately and uses a four-second HTTP limit. Failed fetches back off for a minute and preserve the snapshot, including across offline restarts. Concurrent cold fetches are coalesced. The subscription effort lookup retries from the frontend once a minute, so an initial outage does not hide the selector permanently.

The selected model's published capacity drives both plain-chat history and agent working-context budgets. The context gauge reports unknown when no capability is available. Internally, an unknown model uses a conservative safety budget until data arrives; that budget is not advertised as model capacity. Explicit user context limits still take precedence. Capability discovery starts through the subscription model/effort request; gauge and prompt-budget reads never block on the network.

Vendor ownership from the authenticated list disambiguates routing. When multiple account tiers publish the same ID and no tier is distinguishable, Memo uses their common effort labels and lowest published capacity. This catalog describes the proxy's model metadata, not a guarantee that every account has a larger vendor-advertised context. On the 2026-10-11 live probe, the registry reported 272000 for `gpt-6.1-sol` and 1000000 for `claude-opus-4-6`.

Chat's effort selector and the provider editor query `/api/providers/effort-levels?type=subscriptions&model=<id>`. Only models present in the account list return efforts. The selected effort is sent through the existing OpenAI-compatible `reasoning_effort` request field. Sidecar re-registration preserves the preference; changing models clears a value not supported by the new model.

Verification uses local HTTP catalog fixtures for offline recovery, failed/malformed refreshes, capability matching and 1M context/gauge behavior; the REST effort test excludes catalog-only models, and a Flutter widget test selects and saves a reported effort. An explicit network probe is available with `CGO_ENABLED=1 go test -tags 'sqlite_fts5 upstream' ./internal/modelcatalog -run TestPublishedCatalogSchema -v`. Normal catalog unit tests do not require the internet.
