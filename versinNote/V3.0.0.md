### F2 — Akıllı Sohbet Başlığı (Smart Chat Titles)
İlk mesajın ham metni yerine LLM ile kısa, anlamlı bir başlık otomatik oluşturulur. İkinci mesajdan sonra (ilk exchange tamamlanınca) async goroutine ile title üretilir.

- **Değişen Dosyalar:**
  - `app.go` — `finishStream`'e title generation tetiği eklendi: ilk exchange sonrası `go a.GenerateChatTitle()` çağrılır
  - `frontend/lib/providers/chat_provider.dart` — stream sonrası 2 sn gecikmeli ikinci `chatListProvider` invalidate eklendi (title'ın yetişmesi için)
- **Nasıl Çalışır:** Kullanıcı ikinci mesajı gönderir → LLM yanıtı stream edilir → `finishStream` assistant mesajını kaydeder → `len(GetActiveMessages()) == 2` ise `go GenerateChatTitle()` → LLM'e title prompt'u gönderilir → yanıt session'a `RenameChat` ile yazılır → frontend 2 sn sonra chat list'i tazeleyince yeni başlık görünür
- **Prompt:** `"Based on this conversation excerpt, generate a very short chat title (3–6 words max, no quotes, no punctuation at end):\n\nUser: ...\nAssistant: ...\n\nTitle:"`
- **Fallback:** İlk mesajın tamamı title olarak kalır (LLM title'ı gelene kadar)
- **Etki:** Sohbet listesinde "merhaba" yerine "Python kod yardımı" gibi anlamlı başlıklar görünür

- **Detect Fix'leri:**
  - **OpenRouter model list:** OpenRouter'ın farklı `/models` yanıt yapısı (`data` yerine direkt dizi) için özel parse eklendi

  - **Claude API version header:** Eski `anthropic-version` header'ı ile yeni model isimleri çalışmıyordu → `2023-06-01` olarak sabitlendi

- **Etki:** Kullanıcı yerel GPU'su olmasa bile GPT-4o, Claude, Gemini gibi güçlü modelleri kullanabilir. API key'ler güvenle saklanır. Birden çok sağlayıcı yedekli çalışır.

### F7 — Token Üretimini Durdurma (Stop Streaming)
Kullanıcı mesaj gönderdikten sonra token üretimi devam ederken gönder butonu kırmızı stop (❚❚) butonuna dönüşür. Butona basınca HTTP isteği iptal edilir, backend'de context cancel olur, kısmi yanıt atılır ve UI temizlenir.

- **Değişen Dosyalar:**
  - `frontend/lib/core/api_client.dart` — `sendMessageStream`'e `CancelToken` parametresi eklendi; `DioExceptionType.cancel` yakalanıp sessizce return edilir
  - `frontend/lib/providers/chat_provider.dart` — `MessagesNotifier`'a `_cancelToken` + `_stopped` flag + `stopStreaming()` metodu eklendi; iptal edilince `sendMessage` kısmi yanıtı eklemeden döner
  - `frontend/lib/widgets/chat_input.dart` — `isSending`=true iken gönder butonu kırmızı zeminde stop ikonu gösterir, `onTap` `stopStreaming()` çağırır
- **Nasıl Çalışır:** Kullanıcı mesaj gönderir → buton stop ikonuna döner → "❚❚" tıklanır → `CancelToken.cancel()` → HTTP isteği düşer → backend context iptali ile SSE stream durur → frontend stream'den çıkar, kısmi yanıt silinir, isSending=false
- **Etki:** Kullanıcı yanlış prompt gönderdiğinde veya yanıtı beğenmediğinde anında durdurabilir. GPU/CPU kaynağı boşa harcanmaz.

### F11 — Orkestra Modu (Multi-Model Orchestration)
Çoklu model orkestrasyon sistemi: bir "Şef" (Chief) model görevleri planlar, uzman (Specialist) modellere dağıtır ve sonuçları sentezleyerek tek bir cevap üretir.

- **Değişen Dosyalar:**
  - `internal/orchestra/types.go` — `OrchestraConfig` (enabled, chief_type, chief_model, roles), `OrchestraTask` (role, context, depends_on), `OrchestraPlan`, `OrchestraResult` tipleri
  - `internal/orchestra/conductor.go` — `Conductor` sınıfı: `createPlan` (şef çağrısı + JSON ayrıştırma), `executeTasks` (paralel/bağımlı görev yürütme), `synthesizeResults` (şef son sentez)
  - `internal/orchestra/conductor.go:340-450` — `callWithRetry` (rate limit hatasında `try again in Xs` parse edip 3 kez üstel backoff + jitter ile dener), `isRateLimitError` (hata mesajında rate limit anahtar kelimelerini tanır)
  - `app.go:1330-1380` — `callLLM`/`callLLMStream`'de `orchestraConfig.Enabled` kontrolü, orkestra aktifse `Conductor.Run()` çağrılır
  - `app.go:1400-1420` — `GetOrchestraConfig`/`SetOrchestraConfig` bridge metodları, JSON dosyasına persist (`data/orchestra.json`)
  - `internal/webserver/handlers_flutter.go` — `handleGetOrchestraConfig` (GET `/api/orchestra/config`), `handleSetOrchestraConfig` (PUT `/api/orchestra/config`)
  - `internal/webserver/server.go` — `/api/orchestra/config` route kaydı
  - `frontend/lib/core/api_client.dart` — `getOrchestraConfig()` / `setOrchestraConfig(OrchestraConfig)` API çağrıları
  - `frontend/lib/providers/orchestra_provider.dart` — `orchestraConfigProvider` (AsyncNotifier, toggle + config update metodları)
  - `frontend/lib/widgets/orchestra_config_dialog.dart` — Rol kartları (toggle, model seçici, system prompt edit), "Uzman Ekle" butonu, "Kaydet" aksiyonu
  - `frontend/lib/widgets/settings_dialog.dart` — Orchestra sekmesi (aç/kapa + yapılandırmayı düzenle)
  - `frontend/lib/widgets/chat_input.dart:150-170` — `/plan` slash komutu (mesajı Chief'e gönderip planı gösterir)
- **Nasıl Çalışır:**
  1. Kullanıcı mesaj gönderir → `app.callLLM` orkestra aktif mi kontrol eder
  2. `Conductor.Run()` → `createPlan`: Chief LLM'e roller listesi + kullanıcı mesajı gönderilir, Chief JSON döner (`{"tasks":[{"role":"backend","context":"...","depends_on":[]}], "parallel":true}`)
  3. `executeTasks`: Her task için Specialist provider çağrılır, paralel veya bağımlılık sırasına göre yürütülür
  4. `synthesizeResults`: Tüm task sonuçları Chief'e gönderilir, Chief tek bir tutarlı cevap sentezler
- **Yolda Bulunan ve Düzeltilen Bug'lar:**
  - **Role/Model eşleşmesi**: Chief disabled bir role seçince `ModelType`/`ModelName` boş kalıyor, "unsupported provider type" hatası düşüyordu → `createPlan`'de fallback: disabled role seçilirse ilk enabled role'un model'ine düşer
  - **Provider API Key aktarımı**: `createProviderForType`'da `cfg.Roles[i].ModelType` kullanılıyor, Chief'in Provider'ının API key'i gelmiyordu → `conductor.go:createProviderForType` düzeltildi
  - **JSON `depends_on` tipi**: Chief bazen `depends_on: "frontend"` (string) döndürüyor, `[]string` olarak parse edilemiyordu → `json.Unmarshal` fallback ile string→array dönüşümü eklendi
  - **Config dialog state reset**: Dialog her açılışta config sıfırlanıyor, kullanıcının değişiklikleri kayboluyordu → provider state cache + dialog güncellemesi
  - **Config persist**: `SetOrchestraConfig` JSON yazıp okumuyor, `UpdateLlamaConfig` benzeri merge yapılmıyordu → `writeOrchestraConfig` eklendi, her update dosyaya yazılır
- **Rate Limit Koruma:** `callWithRetry` her provider çağrısını sarar. Rate limit hatası algılanırsa `try again in Xs` parse edilir, bekleme süresi + jitter ile 3 kez tekrar denenir. Chief planlama, task yürütme ve sentez aşamalarının hepsinde aktiftir.
- **Etki:** Tek bir LLM'in yapamayacağı kadar karmaşık işler, farklı modellere bölünerek paralel yürütülür. Her rolün kendine özgü system prompt'u vardır, Chief sadece kısa context üretir (basit JSON, düşük hata). `/plan` komutu ile planlama aşamasını görüntüleme. Rate limitlere karşı dayanıklı.

- **Değişen Dosyalar:**

- **Etki:** Remote access tamamen kapalı. Localhost Flutter API'si etkilenmez.

### K5 — `a.client` / `a.embeddingClient` Race Condition
`App` struct'ına `clientMu sync.RWMutex` eklendi. `a.client` ve `a.embeddingClient` tüm yazma/okuma işlemleri artık bu mutex ile korunuyor.

- **Değişen Dosyalar:**
  - `app.go` — `clientMu` field'ı eklendi, 5 yazma yeri Lock/Unlock, 6 okuma yeri RLock/RUnlock ile korundu
- **Nasıl Çalışır:** Client atanırken Lock alınır. Client okunurken RLock alınır, pointer kopyalanır, kopya üzerinden işlem yapılır. Race condition ve nil-pointer panic önlenir.
- **Etki:** Model start/stop sırasında eşzamanlı istekler güvenli. Nil-client panic riski sıfır.

### K6 — `saveMemoryAsync` RLock→Lock Deadlock
Lock+goroutine pattern'i channel-based worker ile değiştirildi. Tek bir `memorySaveWorker` goroutine kanaldan okur, `storeMu.Lock()` alır, kaydeder. RLock→Lock geçişi tamamen kalktı.

- **Değişen Dosyalar:**

- **Nasıl Çalışır:** `saveMemoryAsync` → `memorySaveCh` → `memorySaveWorker` (tek goroutine) → Lock → SaveInteraction. Kanal 64 kapasiteli, dolarsa drop + log.
- **Etki:** Deadlock riski sıfır. Hafıza kaydetme sıralı ve güvenli.

### K7 — Mesaj Başına AnimationController (UI Jank)
Her `_MessageBubble` widget'ı kendi `AnimationController`'ını oluşturup `FadeTransition` + `SlideTransition` yapıyordu. 50+ mesajda severe frame drop'a neden oluyordu.

### Y3 — Zayıf Anahtar Türetme (Sync Encryption Weak KDF)
Senkronizasyon şifrelemesi tek SHA-256 iterasyonu + sabit tuz kullanıyordu. Zayıf parolalar kaba kuvvetle kırılabilirdi.

- **Değişen Dosyalar:**
  - `internal/cloudsync/crypto.go` — `encrypt`/`decrypt` artık PBKDF2 (600K iterasyon) + rastgele 16-byte tuz kullanıyor
  - `internal/cloudsync/sync_manager.go` — `key [32]byte` → `passphrase string`, encrypt/decrypt çağrıları güncellendi
- **Nasıl Çalışır:** Yeni şifreleme: rastgele tuz → PBKDF2 → AES-256-GCM. Tuz verinin başına eklenir. Eski SHA-256 verileri decrypt'te otomatik fallback ile okunur.
- **Etki:** Senkronizasyon verileri endüstri standardı KDF ile korunur. Eski veriler geriye dönük uyumlu olarak okunabilir.

### Y4 — Sabit Fallback Anahtarı (Hardcoded Fallback Encryption Key)
`hardwareID()` makine kimliği bulamadığında `"memo-fallback-key"` sabit dizesine düşüyordu. Parolası olmayan her makine aynı anahtarı kullanıyordu.

- **Değişen Dosyalar:**
  - `internal/cloudsync/sync_manager.go` — `New()`'de parola boşsa `persistDir/.machine-id` dosyasındaki UUID kullanılır, yoksa oluşturulur
  - `internal/cloudsync/crypto.go` — `hardwareID()` fallback devam ediyor (geriye dönük uyumluluk için), yeni kod `hardwareID()`'e hiç düşmez
- **Nasıl Çalışır:** `loadOrCreateMachineID()` → `.machine-id` dosyasını okur, yoksa `uuid.NewString()` ile oluşturup 0600 izinle kaydeder. Bu ID parola olarak kullanılır.
- **Etki:** Parola yapılandırmamış her makine benzersiz ve kalıcı bir şifreleme anahtarına sahip olur.

### Y11 — OAuth Kanal Yarışı (OAuth `authDone` Channel Race)
`StartAuthFlow` her çağrıldığında yeni bir `chan struct{}` oluşturuyor, `WaitForAuth` eski kanala takılıp kalıyordu. Hızlı art arda OAuth başlatmalarında nadir takılma.

- **Etki:** OAuth akışı artık hızlı yeniden başlatmalarda takılmaz.

### K10 — `processSSEStream` Watcher Goroutine Sızıntısı

### K11 — `callLLMStream` Dolu Kanala Bloke Olma

- **Etki:** İstemci kopunca goroutine saniyeler içinde temizlenir. Kanala bloke olma riski sıfır.

`SaveInteraction` içinde index dosyası `go writeIndexFile(cp)` ile async yazılıyordu. `NewStore` ile yeniden yükleme yapıldığında goroutine henüz tamamlanmamış olabiliyor, index dosyası güncel olmuyordu. Testlerde `Count() = 0` olarak görülüyordu.

- **Değişen Dosya:** `internal/memory/store.go` — `go writeIndexFile(cp)` → `s.writeIndexFile(s.index)` (senkron)
- **Etki:** `SaveInteraction` döndüğünde index dosyası diskte güncel. Reload her zaman doğru sayıda kayıt yükler.

### Async Session Save Race (Sessions)
`Manager.save()` metodu `go func() { os.WriteFile(path, data, 0600) }()` ile async yazıyordu. Test temp dizini temizlenirken goroutine yazmaya devam ediyor, `open: no such file or directory` hatalarına sebep oluyordu.

- **Değişen Dosya:** `internal/sessions/sessions.go` — async goroutine → senkron `os.WriteFile`
- **Etki:** Session dosyaları her zaman senkron yazılır. Goroutine sızıntısı ve temp dizin çakışması önlendi.
