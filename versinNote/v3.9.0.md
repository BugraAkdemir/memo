# Memo v3.9.0 — Release Notes (Work in Progress)

> **Not yet released — development continues.** No tag has been cut for this version; these notes track everything merged since v3.5.5 (August 17–19, 2026) and will keep growing until the version is actually shipped.
>
> The through-line of this stretch is **making things actually correct instead of merely present**: web search went from "inject the user's raw message into every turn" to "the model decides per-message via real tool-calling, at zero cost when it doesn't search"; reasoning-effort control went from static, occasionally-wrong per-vendor tables to live per-model capability discovery after finding out the static version could return a hard 400 on a real request; and a security review of a live self-hosted Raspberry Pi deployment found and closed a genuine auth bypass (a Cloudflare Tunnel forwarding external traffic to loopback, which the old loopback-exemption logic trusted unconditionally) plus three previously-known "High" issues (H04/H05/H10) that had sat open since the last audit.
>
> Also landed: a full LM-Studio-style redesign of the local dev gateway (now speaks both Anthropic- and OpenAI-compatible wire formats, with one-click Claude Code CLI connect and a per-request system-prompt override), a system tray icon with minimize-to-tray, Dream's own configurable schedule, a token-spend breakdown by category in Stats, and a visible "N memories used" badge on replies.

---

## Big Feature: Web Search, Redesigned Twice Over

Web search started this stretch with a real, user-reported bug: the blind (non-agent) search path sent the user's **entire raw message** — filler words, framing, everything — straight to DuckDuckGo's HTML interface as a literal text query, returning close to random results for anything but a bare keyword.

- **First pass:** added an LLM call to distill the message into a short 2–6 word query before searching, with a fallback to the raw message if that call failed.
- **Second, deeper pass:** realized the LLM-cleanup fix treated a design problem as a text-processing problem. The real issue was that blind mode ran a search on *every single message* whenever the toggle was on, whether or not that turn actually needed current information — and now paid for an extra query-extraction call on top of that, every time. Agent Mode already solves "should I search this turn?" for free, since its tool definitions ride along in the same completion request that produces the answer. Plain chat now gets the identical mechanism, scoped to just the `web_search` tool (a dedicated scoped executor/registry, sharing the main agent executor's sandbox/permissions/audit log) instead of the full agent toolset. The old unconditional "searching..." status chunk — which used to show for the whole turn even when the model wouldn't end up searching — is gone; the real one now fires only when a search actually happens.
- **Bug caught during a doc-accuracy pass, not a user report:** the new dispatch path in `routeStream` had no Minimal Mode check. Minimal Mode's whole promise is "zero injection beyond memory" — with it on and web search's toggle also on, a tool definition would still ride along on every request. Fixed and regression-tested.

**Known, accepted gap:** Orchestra Mode + web search + Agent Mode off has no tool-calling to plug this mechanism into, so that specific combination now does no web search at all (it used to get the old blind injection). Rare combination, scoped out deliberately rather than left half-working.

## Big Feature: Reasoning Effort Control, Rebuilt on Live Discovery Instead of Guesses

Reasoning-effort ("low/medium/high", thinking budgets, etc.) had been provider-config-only — Memo never actually sent it, so every request silently ran at whatever default the model picked. Getting this working properly took three passes:

1. **First pass:** per-provider effort levels, with each vendor's actual request shape handled on its own terms — OpenAI/Grok/Groq/Ollama/llama.cpp take a flat `reasoning_effort` string, Claude needs a nested `thinking`+`output_config` pair, Gemini wants a numeric thinking budget instead of a named level, and OpenRouter needs its own nested shape *and* varies by model, so it queries OpenRouter's real `/api/v1/models` response live instead of guessing. A dropdown in the provider config dialog plus a quick-select next to the chat model picker, both hidden automatically for anything with no effort levels to offer.
2. **Found live and fixed:** OpenCode Zen/Go were reusing OpenAI's static table on the assumption that "thin OpenAI-compatible wrapper" implies "same supported values" — it doesn't. Both are aggregators fronting many different vendors behind one endpoint, the same situation OpenRouter is in, except OpenCode's `/models` endpoint (checked live) publishes zero capability metadata, unlike OpenRouter's. There's no way to know per-model which labels actually apply, so a fixed list was actively wrong, not just incomplete. The picker now hides itself for these two instead of guessing.
3. **Replaced entirely:** researching every vendor's real API surface turned up that Claude, Gemini, and Ollama all have genuine per-model capability endpoints Memo wasn't using — and, worse, that sending OpenAI's `reasoning_effort` to a non-reasoning model returns a hard `400 Unsupported parameter`, confirmed live against `gpt-4o`, not a silent no-op as previously assumed. The entire static-table approach is gone. Claude/Gemini/Ollama/OpenRouter now query real per-model capability data before showing any picker at all; everything else shows nothing, since there's no way to check.

**Extended to Agent Mode and Orchestra Mode**, which the first pass had deliberately left out: agent's `Pipeline` and every one of Orchestra's chief/task-execution call sites now carry the same resolved effort level plain chat already used.

## Big Feature: Dev Gateway, Redesigned and Extended

Settings → Developer's local Anthropic-compatible API gateway (the thing that lets Claude Code or any other tool point `ANTHROPIC_BASE_URL` at Memo and use whichever model/provider is configured) got a full pass:

- **Visual redesign**, twice — the first attempt (a 3-equal-column layout) didn't actually resemble LM Studio's own Developer screen on direct comparison; rebuilt around a genuine docs-tree-style nav sidebar (grouped sections, sub-rows that jump the content to the right anchor) matching the real reference. A real runtime bug (`Spacer()` inside a `Wrap`, invisible to static analysis, blanking the whole screen below the top bar) was caught only by a live screenshot and fixed.
- **New: OpenAI-compatible endpoint.** The gateway only ever spoke Anthropic's Messages API; it now also serves `POST /v1/chat/completions` and `GET /v1/models` through the exact same auth/routing/memory/system-prompt pipeline, so anything that only supports an OpenAI-compatible base URL can use it too. A double-encoding bug in tool-call argument serialization was caught by the package's own tests before it ever hit the wire.
- **New: configurable system prompt.** A standing instruction ("always answer in Turkish", etc.) applied to every gateway request, additive on top of whatever the calling tool already sends — deliberately not Memo's own persona, since an external tool supplying its own system prompt shouldn't have Memo's identity forced into it.
- **New: one-click Claude Code CLI connect.** A single toggle writes `ANTHROPIC_BASE_URL`/`ANTHROPIC_API_KEY` directly into the CLI's own `~/.claude/settings.json`, CLI-only (never touches a separate Claude desktop app), with the user's prior values backed up and restored exactly on disconnect. Verified safely — merge logic validated against a disposable scratch-`$HOME` copy first, only then run once against the real file with a full before/after structural comparison.
- **Found immediately after shipping the toggle:** Claude Code sends its own built-in default model name, which the gateway rejects (`model must be "type/model-id"`) — confirmed live via a real error entry in the gateway's own request log. Added a model-selection dropdown right below the connect toggle, backed by the same backup/restore discipline as the base URL.
- **A real, reported design bug fixed along the way:** every `SwitchListTile` in the Developer screen — Require API Key, Use Memory, the new Auto-Connect toggle — relied on Material 3's raw default styling for its *off* state, since `theme.dart` never sets a `switchTheme`. In light mode this read as a washed-out, nearly-invisible pale switch; in dark mode as a track barely distinguishable from the panel background. Fixed with explicit inactive-state colors from Memo's own theme tokens, verified in both themes.
- **Verified with a dedicated test suite** that the gateway genuinely injects nothing beyond what's explicitly configured: a fake backend server captures the literal outbound request, proving default config passes messages through byte-for-byte, a configured system prompt adds exactly that text and nothing else, and turning on "Use Memory" without the global memory system also on stays a no-op.

## Big Feature: System Tray Icon

Requested directly: an LM-Studio-style tray icon, since LM Studio's own tray menu (Open / server status / model status / Quit) was the reference point. Right-clicking Memo's new tray icon shows "Open Memo", a status line for whether a local model is currently running, and "Quit Memo". A new **"Minimize to System Tray"** toggle in Settings → General (off by default, so nothing changes unless turned on) makes closing the main window hide it to the tray instead of quitting outright — the app keeps running in the background, same as the reference behavior. Desktop-only (Linux/macOS/Windows); a total no-op on web, where the underlying packages have no implementation. Verified live on a real Linux/Wayland desktop across all four combinations: tray icon + menu render correctly, closing the window quits fully with the setting off (default) and stays running with it on, and the tray's own Quit does terminate the process.

A build-system issue turned up along the way: `flutter build linux` failed outright once the tray package was added, because its Linux plugin calls an older, now-deprecated `libappindicator` API and the project treats every compiler warning as a hard error. Fixed by downgrading just that one warning class to non-fatal, without loosening `-Werror` for anything else.

## Big Feature: Dream Gets Its Own Schedule

Dream (the deeper memory-consolidation pass) used to piggyback on the fixed 24-hour consolidation loop with no way to configure it separately. It now has its own scheduler, independently configurable initial delay and interval, and a manual "run now" trigger — surfaced in a new Settings tab (grouped under Memory) with an inline before/after fact-count readout. A real bug surfaced while wiring this up: `mergeMemoriesLLM` was calling the provider router directly instead of going through the shared routing helper every other LLM call in the memory package uses, so consolidation silently did nothing at all on a local-only setup with no external provider configured.

## Big Feature: Where Are Tokens Actually Going?

Memo's own background calls — Dream, fact extraction, mood, title generation, learning, proactive nudges — were completely invisible in the Stats tab; only the visible streaming chat path ever recorded usage at all. Every usage event now carries a category (`chat`, `agent`, `dream`, `fact_extraction`, `mood`, `title`, `learning`, `proactive`, ...), migrated one call site at a time so any single category could be reverted independently if something went wrong. Stats now shows a **"What It's Being Used For"** breakdown ranked by actual token spend, not request count — a handful of large Dream batches should (and now does) outrank many tiny title-generation calls even with far fewer requests. The day-range selector (7/30/90) is also now actually wired to the data instead of always fetching a hardcoded window, and a new "Pinned Fact Tokens" card shows the real token cost of everything pinned to memory permanently.

## Big Feature: "How Many Memories Did This Actually Use?"

Memory retrieval has always been invisible — the only signal it happened was a log line that never left the terminal, leaving no way to tell whether "hafıza" genuinely contributed to a given reply. Replies now show a small brain icon + count in the hover metadata row (next to the timestamp/copy button) reporting exactly how many memories were retrieved for that turn, both live as the reply streams in and persisted so it's still visible after a reload or from another device.

## Fixed: Incognito Mode Could Silently Eat Replies After a Refresh

Reported live from a real self-hosted deployment: AI replies would stream to screen once and then vanish for good after a page reload, with no error. Root cause — the frontend's incognito toggle always started at `false` and never checked the backend's real (single, global) incognito flag on load, so a reload after leaving incognito on in an earlier tab showed a completely normal-looking chat while the backend kept quietly diverting every reply into the incognito-only buffer instead of the visible session. Fixed by syncing the real state on load; also added a translucent red tint over the chat background while incognito is active, and a small red indicator dot on the nav rail logo itself (visible from every tab, not just chat) so it can't go unnoticed the way it did here.

## Security Fixes

- **Cloudflare Tunnel auth bypass**, found and confirmed live via SSH on a real self-hosted Raspberry Pi deployment. The loopback exemption (a request from `127.0.0.1` needs no credential, since only local software can produce that source address) didn't account for a local reverse proxy or tunnel forwarding *external* traffic to that same loopback address — confirmed live with a Cloudflare Tunnel ingress rule pointing at `http://localhost:8090` (an ordinary, commonly-suggested self-hosting pattern), where `cloudflared`'s host-network container made every request appear to originate from loopback, indistinguishable by IP alone from the real desktop client. Anyone on the public internet could reach every `/api/` route with zero credential. Fixed by treating the presence of a standard proxy-forwarding header (`X-Forwarded-For`, `X-Real-Ip`, `Cf-Connecting-Ip`, `Forwarded`) on an otherwise-loopback request as a "don't extend trust here" signal, never as a client-identity source. The genuine desktop client never sets any of these headers, so legitimate local use is unaffected.
- **Setup wizard reappearing per-origin.** Completion state lived only in the browser's own localStorage, scoped per origin — a backend reachable from more than one address (a LAN IP and a tunnel hostname pointing at the same install, the exact setup that surfaced the bug above) kept re-showing the wizard on whichever origin hadn't independently completed it there, even though the backend was already fully configured. Completion is now a durable server-side fact every client checks.
- **H04 — ngrok binary download had no integrity check at all.** A pinned checksum isn't realistically possible here (ngrok publishes none for this rolling "stable" URL, and the content changes on every release), so what's added instead is a check that the response's leading bytes genuinely match the archive format its extension promises — catches a real, observed failure mode where a CDN error page gets served with a 200 status instead of the actual binary. The real checksum-pinning gap is left open and documented in code.
- **H05 — a literal underscore in a WhatsApp message search silently acted as a wildcard.** Not a security issue (the query was already parameterized), just wrong results — `SearchMessages`'s `LIKE` pattern wasn't escaping SQL's own `%`/`_` wildcard characters. Fixed.
- **H10 — the agent tool-call audit log wasn't actually being audited.** Every entry describing what an agent session did (file writes, commands run, results, errors) lived only in an in-memory slice capped at 1000 entries, for a feature whose entire stated purpose is auditing — gone for good past that cap or any restart. Every entry is now also appended to a persistent, append-only file on disk.

## Small Fixes

- **Execute-bit regression, found across multiple install paths.** `get-memo-server.sh` copied binaries into place without re-applying the execute bit afterward (archives don't reliably preserve it) — `llama-server` landed non-executable on fresh self-hosted installs. The same gap existed in the ARM desktop installer, the CI build scripts that produce the actual downloadable release archives, and the local macOS release script's embedded launcher. All fixed to match the pattern already correct elsewhere.
- `providers.json` (encrypted-at-rest provider configs, including API keys) was silently excluded from the uninstall backup across all three uninstall scripts — found live during a real uninstall/reinstall cycle. Now included.
- A SQL `NULL` from an empty-store aggregate crashed the Stats query outright on a completely fresh install before the first memory was ever saved.

## Still Open

- Orchestra Mode's single-completion path has no tool-calling to plug the new scoped web-search mechanism into — that specific combination (Orchestra + web search + Agent Mode off) currently does no search at all.
- The live chat view can show a turn as already finished while an Orchestra task's permission request is still pending in the background (the backend itself handles this correctly; the dialog just doesn't always appear on screen while it's happening) — carried over from v3.5.5, not yet revisited.
- Reasoning-effort's fallback-to-a-different-vendor path (when the exact requested provider type isn't configured) doesn't carry an effort level — the fallback vendor's own semantics can't be inferred from the original request.
- ngrok's binary download has no real checksum pin (see H04 above) — genuine tamper-resistance against a compromised CDN would require pinning to one specific ngrok version, a deliberate trade-off not made unilaterally.
- Built-in TLS, and starting/stopping a Tailscale/ngrok tunnel from the CLI, remain not done (carried over from v3.5.5).
