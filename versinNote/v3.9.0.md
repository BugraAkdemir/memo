# Memo v3.9.0 — Release Notes (Work in Progress)

> **Not yet released — development continues.** No tag has been cut for this version; these notes track everything merged since v3.5.5 (August 17–22, 2026) and will keep growing until the version is actually shipped.
>
> The through-line of this stretch is **making things actually correct instead of merely present**: web search went from "inject the user's raw message into every turn" to "the model decides per-message via real tool-calling, at zero cost when it doesn't search"; reasoning-effort control went from static, occasionally-wrong per-vendor tables to live per-model capability discovery after finding out the static version could return a hard 400 on a real request; and a security review of a live self-hosted Raspberry Pi deployment found and closed a genuine auth bypass (a Cloudflare Tunnel forwarding external traffic to loopback, which the old loopback-exemption logic trusted unconditionally) plus three previously-known "High" issues (H04/H05/H10) that had sat open since the last audit.
>
> Also landed: a full LM-Studio-style redesign of the local dev gateway (now speaks both Anthropic- and OpenAI-compatible wire formats, with one-click Claude Code CLI connect and a per-request system-prompt override), a system tray icon with minimize-to-tray, Dream's own configurable schedule, a token-spend breakdown by category in Stats, and a visible "N memories used" badge on replies.
>
> And, right at the end of this stretch: Memo can now be talked to from **WhatsApp** (message yourself, it replies) and, brand new, from **Telegram** (connect a bot, message it, it replies) — plus a full mobile navigation redesign that hides the desktop NavRail behind a hamburger drawer on narrow screens.
>
> Right after that: routines (scheduled automations) became something you can create, list, and cancel just by talking to Memo from WhatsApp or Telegram — no need to open the Routines tab — with a hard security rule baked in from the start (the model can never pick an arbitrary delivery target; it's always locked to the surface you're talking to it from, plus a channel you explicitly ask for and already have connected). And a late-stretch live test surfaced the most consequential bug of this release: self-chat's agent tools, including the ones just described, were never actually reachable at all.
>
> The final stretch (August 22) closed out four more things, all driven by direct user requests and, for two of them, real live bug reports with screenshots: routines had the same "was it actually reachable" problem self-chat itself just had — fixed the same way, unconditionally, not by trusting a one-shot text classification made once at routine-creation time. Self-hosted multi-account got real per-capability permissions, not just admin/user — an account can now be limited to chat only, or opted into specific things (models, memory, agent, calendar, WhatsApp, Telegram, routines) one checkbox at a time. The CLI closed its last self-hosting gap (account management over SSH) and grew two new scripting flags for inspecting an existing chat. And Memo gained a new external provider — Kilo Code's AI Gateway — plus a real fix to a Provider Settings screen that, once actually clicked through by a live user, turned out to look and behave worse than anyone had noticed from reading the code alone.

## Big Feature: Web Search, Redesigned Twice Over

Web search started this stretch with a real, user-reported bug: the blind (non-agent) search path sent the user's **entire raw message** — filler words, framing, everything — straight to DuckDuckGo's HTML interface as a literal text query, returning close to random results for anything but a bare keyword.

- **First pass:** added an LLM call to distill the message into a short 2–6 word query before searching, with a fallback to the raw message if that call failed.
- **Second, deeper pass:** realized the LLM-cleanup fix treated a design problem as a text-processing problem. The real issue was that blind mode ran a search on *every single message* whenever the toggle was on, whether or not that turn actually needed current information — and now paid for an extra query-extraction call on top of that, every time. Agent Mode already solves "should I search this turn?" for free, since its tool definitions ride along in the same completion request that produces the answer. Plain chat now gets the identical mechanism, scoped to just the `web_search` tool (a dedicated scoped executor/registry, sharing the main agent executor's sandbox/permissions/audit log) instead of the full agent toolset. The old unconditional "searching..." status chunk — which used to show for the whole turn even when the model wouldn't end up searching — is gone; the real one now fires only when a search actually happens.
- **Bug caught during a doc-accuracy pass, not a user report:** the new dispatch path in `routeStream` had no Minimal Mode check. Minimal Mode's whole promise is "zero injection beyond memory" — with it on and web search's toggle also on, a tool definition would still ride along on every request. Fixed and regression-tested.

**Known, accepted gap:** Orchestra Mode + web search + Agent Mode off has no tool-calling to plug this mechanism into, so that specific combination now does no web search at all (it used to get the old blind injection). Rare combination, scoped out deliberately rather than left half-working.

## Big Feature: Reasoning Effort Control, Rebuilt on Live Discovery Instead of Guesses

Reasoning-effort ("low/medium/high", thinking budgets, etc.) had been provider-config-only — Memo never actually sent it, so every request silently ran at whatever default the model picked. Getting this working properly took three passes:

1. **First pass:** per-provider effort levels, with each vendor's actual request shape handled on its own terms — OpenAI/Grok/Groq/Ollama/llama.cpp take a flat `reasoning_effort` string, Claude needs a nested `thinking`+`output_config` pair, Gemini wants a numeric thinking budget instead of a named level, and OpenRouter needs its own nested shape *and* varies by model, so it queries OpenRouter's real `/api/v1/models` response live instead of guessing. A dropdown in the provider config dialog plus a quick-select next to the chat model picker, both hidden automatically for anything with no effort levels to offer.
2. **Found live and fixed:** OpenCode Zen/Go were reusing OpenAI's static table on the assumption that "thin OpenAI-compatible wrapper" implies "same supported values" — it doesn't. Both are aggregators fronting many different vendors behind one endpoint, the same situation OpenRouter is in, except OpenCode's `/models` endpoint (checked live) publishes zero capability metadata, unlike OpenRouter's. There's no way to know per-model which labels actually apply, so a fixed list was actively wrong, not just incomplete. The picker now hides itself for these two instead of guessing.
3. **Replaced entirely:** researching every vendor's real API surface turned up that Claude, Gemini, and Ollama all have genuine per-model capability endpoints Memo wasn't using — and, worse, that sending OpenAI's `reasoning_effort` to a non-reasoning model returns a hard `400 Unsupported parameter`, confirmed live against `gpt-4o`, not a silent no-op as previously assumed. The entire static-table approach is gone. Claude/Gemini/Ollama/OpenRouter now query real per-model capability data before showing any picker at all; everything else shows nothing, since there's no way to check.

**Extended to Agent Mode and Orchestra Mode**, which the first pass had deliberately left out: agent's `Pipeline` and every one of Orchestra's chief/task-execution call sites now carry the same resolved effort level plain chat already used.

## Big Feature: Dev Gateway, Redesigned and Extended

Settings → Developer's local Anthropic-compatible API gateway (the thing that lets Claude Code or any other tool point `ANTHROPIC_BASE_URL` at Memo and use whichever model/provider is configured) got a full pass:

- **Visual redesign**, twice — the first attempt (a 3-equal-column layout) didn't actually resemble LM Studio's own Developer screen on direct comparison; rebuilt around a genuine docs-tree-style nav sidebar (grouped sections, sub-rows that jump the content to the right anchor) matching the real reference. A real runtime bug (`Spacer()` inside a `Wrap`, invisible to static analysis, blanking the whole screen below the top bar) was caught only by a live screenshot and fixed.
- **New: OpenAI-compatible endpoint.** The gateway only ever spoke Anthropic's Messages API; it now also serves `POST /v1/chat/completions` and `GET /v1/models` through the exact same auth/routing/memory/system-prompt pipeline, so anything that only supports an OpenAI-compatible base URL can use it too. A double-encoding bug in tool-call argument serialization was caught by the package's own tests before it ever hit the wire.
- **New: configurable system prompt.** A standing instruction ("always answer in Turkish", etc.) applied to every gateway request, additive on top of whatever the calling tool already sends — deliberately not Memo's own persona, since an external tool supplying its own system prompt shouldn't have Memo's identity forced into it.
- **New: one-click Claude Code CLI connect.** A single toggle writes `ANTHROPIC_BASE_URL`/`ANTHROPIC_API_KEY` directly into the CLI's own `~/.claude/settings.json`, CLI-only (never touches a separate Claude desktop app), with the user's prior values backed up and restored exactly on disconnect. Verified safely — merge logic validated against a disposable scratch-`$HOME` copy first, only then run once against the real file with a full before/after structural comparison.
- **Found immediately after shipping the toggle:** Claude Code sends its own built-in default model name, which the gateway rejects (`model must be "type/model-id"`) — confirmed live via a real error entry in the gateway's own request log. Added a model-selection dropdown right below the connect toggle, backed by the same backup/restore discipline as the base URL.
- **A real, reported design bug fixed along the way:** every `SwitchListTile` in the Developer screen — Require API Key, Use Memory, the new Auto-Connect toggle — relied on Material 3's raw default styling for its *off* state, since `theme.dart` never sets a `switchTheme`. In light mode this read as a washed-out, nearly-invisible pale switch; in dark mode as a track barely distinguishable from the panel background. Fixed with explicit inactive-state colors from Memo's own theme tokens, verified in both themes.
- **Verified with a dedicated test suite** that the gateway genuinely injects nothing beyond what's explicitly configured: a fake backend server captures the literal outbound request, proving default config passes messages through byte-for-byte, a configured system prompt adds exactly that text and nothing else, and turning on "Use Memory" without the global memory system also on stays a no-op.

## Big Feature: System Tray Icon

Requested directly: an LM-Studio-style tray icon, since LM Studio's own tray menu (Open / server status / model status / Quit) was the reference point. Right-clicking Memo's new tray icon shows "Open Memo", a status line for whether a local model is currently running, and "Quit Memo". A new **"Minimize to System Tray"** toggle in Settings → General (off by default, so nothing changes unless turned on) makes closing the main window hide it to the tray instead of quitting outright — the app keeps running in the background, same as the reference behavior. Desktop-only (Linux/macOS/Windows); a total no-op on web, where the underlying packages have no implementation. Verified live on a real Linux/Wayland desktop across all four combinations: tray icon + menu render correctly, closing the window quits fully with the setting off (default) and stays running with it on, and the tray's own Quit does terminate the process.

A build-system issue turned up along the way: `flutter build linux` failed outright once the tray package was added, because its Linux plugin calls an older, now-deprecated `libappindicator` API and the project treats every compiler warning as a hard error. Fixed by downgrading just that one warning class to non-fatal, without loosening `-Werror` for anything else.

## Big Feature: Dream Gets Its Own Schedule

Dream (the deeper memory-consolidation pass) used to piggyback on the fixed 24-hour consolidation loop with no way to configure it separately. It now has its own scheduler, independently configurable initial delay and interval, and a manual "run now" trigger — surfaced in a new Settings tab (grouped under Memory) with an inline before/after fact-count readout. A real bug surfaced while wiring this up: `mergeMemoriesLLM` was calling the provider router directly instead of going through the shared routing helper every other LLM call in the memory package uses, so consolidation silently did nothing at all on a local-only setup with no external provider configured.

## Big Feature: Where Are Tokens Actually Going?

Memo's own background calls — Dream, fact extraction, mood, title generation, learning, proactive nudges — were completely invisible in the Stats tab; only the visible streaming chat path ever recorded usage at all. Every usage event now carries a category (`chat`, `agent`, `dream`, `fact_extraction`, `mood`, `title`, `learning`, `proactive`, ...), migrated one call site at a time so any single category could be reverted independently if something went wrong. Stats now shows a **"What It's Being Used For"** breakdown ranked by actual token spend, not request count — a handful of large Dream batches should (and now does) outrank many tiny title-generation calls even with far fewer requests. The day-range selector (7/30/90) is also now actually wired to the data instead of always fetching a hardcoded window, and a new "Pinned Fact Tokens" card shows the real token cost of everything pinned to memory permanently.

## Big Feature: "How Many Memories Did This Actually Use?"

Memory retrieval has always been invisible — the only signal it happened was a log line that never left the terminal, leaving no way to tell whether "hafıza" genuinely contributed to a given reply. Replies now show a small brain icon + count in the hover metadata row (next to the timestamp/copy button) reporting exactly how many memories were retrieved for that turn, both live as the reply streams in and persisted so it's still visible after a reload or from another device.

## Big Feature: Talk to Memo From WhatsApp — Message Yourself, It Replies

Requested directly: message yourself on WhatsApp ("Message Yourself" chat) and have Memo pick it up and reply, turning your own phone into another interface for talking to Memo — on top of the existing "WhatsApp Chat" agent tool, which could already read/send messages but never auto-replied to anything on its own. Opt-in (off by default), since it's the one WhatsApp feature that autonomously sends outgoing messages rather than just reading or being explicitly told to send one.

Landed in several live-tested rounds, each closing a real bug the user actually hit:

- **Core mechanism:** an incoming self-chat message routes through a dedicated background session (the same memory/intent/mood pipeline normal chat uses via `SendMessageStreamTo`), without touching whatever chat is open in the UI.
- **Root-cause bug: the assistant never actually replied.** WhatsApp's newer Linked-ID (`@lid`) addressing means a self-chat's `ChatJID` doesn't always arrive as the phone-number form the original matching logic checked — confirmed live against a real account, where the real self-chat JID only ever showed up as the `@lid` form. Fixed to match either form.
- **Native "typing…" indicator** while a reply is generating, refreshed periodically since WhatsApp clears it client-side if not renewed — reuses WhatsApp's own chat-presence API rather than faking it with a placeholder message.
- **Stray digits/words leaking into replies** (a bare "9", "web_searchweb_search") — the non-streaming self-chat path collapsed every chunk into one string but only filtered out one specific status-marker type, letting status/memory-count markers meant for the UI's own SSE parsing bleed into plain text. Fixed by flipping the filter (only genuine text chunks pass through, not just the one marker type spotted first) — this also silently fixed the same leak on the plain `/api/send` endpoint.
- **Slash commands** (`/new`, `/agent on|off`, `/web on|off`, `/status`, `/help`) so a self-chat conversation can control Memo without ever opening the app.
- **Command replies were hardcoded Turkish**, caught by a direct user question ("bu hardcode değil demi, uygulama dilim en ise en çıkacak demi"). Now follow the same `Identity.UILanguage` setting the Flutter GUI's own language toggle writes to, read fresh on every call — a headless backend serves the GUI and WhatsApp concurrently, so it can't just snapshot a language once at startup the way a short-lived CLI process does.
- **WhatsApp's connection UI moved into Settings** (out of its own nav tab) alongside the assistant toggle — the dedicated tab's chat/message-browsing UI was redundant with the agent tool and normal chat, and was itself the source of a real bug (a fast navigate-in/navigate-out could dispose the screen mid-poll — "Cannot use 'ref' after the widget was disposed" — permanently killing the recursive status poll, reported live as getting stuck on "Preparing QR code..." forever).

## Big Feature: Telegram Support — the Same Thing, With a Bot Instead

Immediate follow-up to WhatsApp's self-chat assistant: **connect a Telegram bot** (Settings → Telegram, paste a token from @BotFather) and talk to Memo through it the same way. Deliberately narrower in scope than WhatsApp: a Telegram bot can only ever see messages sent directly to it — there's no equivalent of WhatsApp's full account visibility without the much heavier phone-number-login user API — so this is a chat interface only, not a message-reading/sending agent tool.

- **Security model, built in from the start rather than bolted on:** unlike a personal WhatsApp account, a bot token is reachable by anyone who finds it. Whoever sends the bot its very first message is locked in as its **permanent owner**; every message from anyone else is silently ignored from then on (no reply, no "this bot is private" leak — a stranger who finds the bot just gets nothing back).
- **Same command set and UX as WhatsApp's assistant** — `/new`, `/agent`, `/web`, `/status`, `/help`, the same dedicated-background-session pattern, the same "typing…" indicator while a reply generates, replies following `Identity.UILanguage` from day one (no separate hardcoded-Turkish bug to rediscover this time).
- **No new dependency** — a small, purpose-built long-polling Bot API client (`internal/telegram`) instead of pulling in a bot framework for this scope. The bot token is encrypted at rest with the same machine key `providers.json` already uses.
- A step-by-step "how to connect" walkthrough is built directly into the Settings tab for anyone who's never made a Telegram bot before.

## Big Feature: Routines, Now Usable From WhatsApp and Telegram

Requested directly: routines (scheduled automations) shouldn't require opening the Routines tab at all — typing "memo hergün saat 9'da bana sistem bilgilerini gönder" straight into a WhatsApp or Telegram self-chat should just work. Landed as three new agent tools (`create_routine`, `list_routines`, `cancel_routine`) plus several rounds of live-testing-driven fixes:

- **Hard security constraint, decided up front:** unlike the Routines tab's own human-driven channel picker, the model must never be able to choose an arbitrary WhatsApp contact or Telegram chat as a delivery target. `resolveRoutineDeliveryTarget` always forces delivery to whichever surface the routine is being created from; the *other* channel is only ever added if the user's own text explicitly asks for it *and* that channel is actually connected — verified with unit tests that pass a `nil` WhatsApp client/Telegram store and confirm the forced-target code path never falls through to reading live connectivity state.
- **Mobile delivery removed entirely** — `DeliveryMobile` and its payload were pulled from the routine type, the scheduler loop, the webserver's mobile-ready endpoint, and the Routines tab's channel picker, since there's no mobile app in active use to receive it.
- **Reversed after live testing:** routines created via chat originally tied `AutoApproveTools` to whatever the creating surface's live `/auto-perm` setting happened to be at that moment — live-tested and rejected (a routine firing hours or days later shouldn't depend on a per-chat setting that might have silently changed, or reset on a `/new`, in between). Replaced with a fixed standing policy: a chat-created routine that needs agent mode always auto-approves its own tool calls, and routines always run with agent mode and web search available regardless of either surface's global toggle state.
- **Multi-channel delivery bug:** asking from WhatsApp self-chat for a routine delivered to "Telegram ve WhatsApp'tan" was silently collapsed to WhatsApp only — the forced-target logic wasn't checking the user's own text for an explicit request for the *other*, already-connected channel. Fixed to honor it.
- **No way to list or cancel a routine created this way** — added `list_routines` and `cancel_routine` to close the loop the user asked for directly ("iptal edebilir miyim").
- **`/auto-perm on|off`** added to both WhatsApp and Telegram self-chat commands. Found live: an agent tool call needing permission from inside self-chat had no way to actually ask — it silently timed out with no visible prompt. `/auto-perm on` makes self-chat auto-approve tool calls; off makes it genuinely ask and wait for a yes/no reply in the same chat.

## Fixed: Self-Chat's Agent Tools Were Never Actually Reachable

The most consequential bug of this stretch, caught only because the user pasted a real WhatsApp transcript where Memo, asked to set up a daily routine, answered as if `create_routine` and every other agent tool described above simply didn't exist — generic, hallucinated "I can't do that yet" text with zero real capability awareness.

Root cause, traced with the codebase's dependency graph rather than guessed at: `SendMessageStreamTo` — the only path WhatsApp/Telegram self-chat ever used — decides whether agent tools are available via `forceAgent = sessions.Manager.IsAgentChat(chatID)`, and `IsAgentChat` is just `session.ProjectPath != ""`, true only for project-scoped "Agent Chat"s created through `NewAgentChat`. Self-chat's own session is deliberately created through `NewBackgroundChat` instead (so it never hijacks whatever chat is open in the UI), which never sets `ProjectPath` — so `IsAgentChat` was always false, `forceAgent` was always false, and tool access fell back entirely to the **global** `agentEnabled` toggle, off by default with no way to turn it on from inside self-chat short of typing `/agent on` first. Every routine tool, `web_search`, and `whatsapp_send` had been genuinely unreachable from self-chat this entire time; every earlier "fixed and tested" round above only ever verified the tools themselves worked once agent mode was already on, never that self-chat could reach that state on its own.

Fixed with a new `SendMessageStreamToAsAgent`, used only by self-chat, that forces `forceAgent = true` unconditionally — the same thing `runAgentRoutine` already did for routine firings, just never applied to normal incoming self-chat messages. Self-chat's real safety boundary was always meant to be `/auto-perm`'s permission-asking flow, not a second, easy-to-forget "is agent mode nominally on" gate sitting in front of it. Confirmed live by the user afterward: a real WhatsApp self-chat request now genuinely runs a web search and returns real, current results at the right time.

Separately, raised in the same conversation: web search should default to on generally, not only once a routine or self-chat forces it. `WebSearchConfig.Enabled`'s default flipped from `false` to `true` — the old justification ("hits the network every message") no longer applies now that web search runs through real tool-calling, where the model decides per-turn whether to search at all, at zero cost on turns it doesn't. Existing installs are unaffected, since `Load()` always overlays their own `config.yaml`, which already carries an explicit value.

## Fixed: Incognito Mode Could Silently Eat Replies After a Refresh

Reported live from a real self-hosted deployment: AI replies would stream to screen once and then vanish for good after a page reload, with no error. Root cause — the frontend's incognito toggle always started at `false` and never checked the backend's real (single, global) incognito flag on load, so a reload after leaving incognito on in an earlier tab showed a completely normal-looking chat while the backend kept quietly diverting every reply into the incognito-only buffer instead of the visible session. Fixed by syncing the real state on load; also added a translucent red tint over the chat background while incognito is active, and a small red indicator dot on the nav rail logo itself (visible from every tab, not just chat) so it can't go unnoticed the way it did here.

## Security Fixes

- **Cloudflare Tunnel auth bypass**, found and confirmed live via SSH on a real self-hosted Raspberry Pi deployment. The loopback exemption (a request from `127.0.0.1` needs no credential, since only local software can produce that source address) didn't account for a local reverse proxy or tunnel forwarding *external* traffic to that same loopback address — confirmed live with a Cloudflare Tunnel ingress rule pointing at `http://localhost:8090` (an ordinary, commonly-suggested self-hosting pattern), where `cloudflared`'s host-network container made every request appear to originate from loopback, indistinguishable by IP alone from the real desktop client. Anyone on the public internet could reach every `/api/` route with zero credential. Fixed by treating the presence of a standard proxy-forwarding header (`X-Forwarded-For`, `X-Real-Ip`, `Cf-Connecting-Ip`, `Forwarded`) on an otherwise-loopback request as a "don't extend trust here" signal, never as a client-identity source. The genuine desktop client never sets any of these headers, so legitimate local use is unaffected.
- **Setup wizard reappearing per-origin.** Completion state lived only in the browser's own localStorage, scoped per origin — a backend reachable from more than one address (a LAN IP and a tunnel hostname pointing at the same install, the exact setup that surfaced the bug above) kept re-showing the wizard on whichever origin hadn't independently completed it there, even though the backend was already fully configured. Completion is now a durable server-side fact every client checks.
- **H04 — ngrok binary download had no integrity check at all.** A pinned checksum isn't realistically possible here (ngrok publishes none for this rolling "stable" URL, and the content changes on every release), so what's added instead is a check that the response's leading bytes genuinely match the archive format its extension promises — catches a real, observed failure mode where a CDN error page gets served with a 200 status instead of the actual binary. The real checksum-pinning gap is left open and documented in code.
- **H05 — a literal underscore in a WhatsApp message search silently acted as a wildcard.** Not a security issue (the query was already parameterized), just wrong results — `SearchMessages`'s `LIKE` pattern wasn't escaping SQL's own `%`/`_` wildcard characters. Fixed.
- **H10 — the agent tool-call audit log wasn't actually being audited.** Every entry describing what an agent session did (file writes, commands run, results, errors) lived only in an in-memory slice capped at 1000 entries, for a feature whose entire stated purpose is auditing — gone for good past that cap or any restart. Every entry is now also appended to a persistent, append-only file on disk.

## Small Fixes

- **Execute-bit regression, found across multiple install paths.** `get-memo-server.sh` copied binaries into place without re-applying the execute bit afterward (archives don't reliably preserve it) — `llama-server` landed non-executable on fresh self-hosted installs. The same gap existed in the ARM desktop installer, the CI build scripts that produce the actual downloadable release archives, and the local macOS release script's embedded launcher. All fixed to match the pattern already correct elsewhere.
- `providers.json` (encrypted-at-rest provider configs, including API keys) was silently excluded from the uninstall backup across all three uninstall scripts — found live during a real uninstall/reinstall cycle. Now included.
- A SQL `NULL` from an empty-store aggregate crashed the Stats query outright on a completely fresh install before the first memory was ever saved.
- Settings → General's Streaming/Memory switches carried the same invisible-when-off styling bug already fixed for the Developer screen's switches (above) — same root cause (`theme.dart` never set a `switchTheme`), fixed with the same explicit inactive-state colors.

## Fixed: Routines Had the Same "Was It Actually Reachable" Problem Self-Chat Just Had

Direct user report, right after the self-chat agent-access fix above: "rutinlerde halen agent özelliği bir süre sonra off oluyo" — a routine's ability to use agent tools or web search still seemed to disappear on its own. It wasn't disappearing at runtime; it had never been reliably granted in the first place. `Routine.AgentMode` was set exactly once, at creation time, from the text-extraction LLM's one-shot guess at whether the routine's free-text description sounded like it needed "real" actions — a routine like "her gün yapay zeka haberlerini getir" (read-only, just wants a summary) was correctly classified as not needing agent mode, which meant it got **zero** tool access, permanently, including `web_search`, no matter what it later turned out to need. There was no way to fix this short of deleting and recreating the routine with different wording and hoping the classifier guessed differently next time.

Fixed by removing the gate entirely rather than trying to make the guess better: every routine — including ones already sitting in the store with a stale `AgentMode: false` from before this fix, since the check that used to branch on that field is gone, not just skipped for new routines — now runs through the same full agent pipeline routines with `AgentMode: true` already used. `web_search` is Safe-DangerLevel, so it's always usable with zero permission friction; anything genuinely dangerous (running a command, writing a file) still respects the routine's own `AutoApproveTools` setting and the live permission-ask flow exactly as before — this widens what a routine's tool *can* reach, it doesn't loosen what it's allowed to do once there. The old deterministic context pre-fetch (today's calendar agenda, a specific WhatsApp chat's recent messages, a web search) is preserved too, folded into the same prompt as a guaranteed floor rather than something the model now has to remember to fetch itself via a tool call.

## Big Feature: Self-Hosted Multi-Account Gets Real Per-Capability Permissions

Faz 5.1 (v3.5.5) gave self-hosted Memo admin/user accounts, but "user" was one fixed bundle — full chat, agent, memory, calendar, and WhatsApp access, minus only server administration. Requested directly, with the exact shape spelled out: an admin creating an account should be able to leave every box unchecked (chat only) or opt in specific capabilities one at a time — **Models** (switching providers, the Model Store), **Memory**, **Agent** (tool/command execution), **Calendar**, **WhatsApp**, **Telegram**, **Routines** — shown as checkboxes at account creation, editable afterward without recreating the account.

- **Fail-closed by design, the opposite of the account system's own admin gate.** A brand-new "user" account with nothing checked can only chat — every other capability has to be deliberately granted, not deliberately revoked. Enforced server-side (`requirePermission`/`requirePermissionStrict` wrapping roughly 25 endpoints across models/providers, memory, agent, calendar, WhatsApp, Telegram, and routines) with the exact same fail-open shape the existing admin-only gate already used for everything else: no credential at all (local desktop use), an unrecognized or expired session, or an admin session all pass through unaffected — only a *recognized* "user"-role session missing a specific box gets turned away. Every pre-existing install with no accounts configured is completely unaffected.
- **Memory is the one permission that also gates reads, not just writes** — the whole point of denying it is that the account can't see what's in shared memory at all, not merely that it can't add to it. Every other permission only gates the mutating/management actions for that area (GET requests some parts of the app poll ambiently — like the chat header's active-model badge — keep working even for a restricted account, since blocking those would break plain chat, not just the specific screen the permission is meant to hide).
- **The client-side half — hiding, not just blocking.** A restricted account's Settings dialog no longer even shows the Providers, Memory, Memory Import, Dream, WhatsApp, or Telegram tabs; the account-creation dialog's checkbox list, and a matching "edit permissions" dialog for changing them after the fact, live right next to where roles are already managed.
- **Known, honestly-scoped limitation:** only the Settings-dialog tabs are hidden this way so far — the top-level Model Store/Calendar/Routines screens aren't yet gated the same way (the backend still blocks their mutating actions regardless). And Agent permission can't fully isolate a restricted account yet, because agent mode is still one flag shared by the entire backend process, not scoped per account — denying it stops that account from turning agent mode on itself, but a plain message from that account can still ride along if some other session already left agent mode on globally. Real per-account isolation is a materially bigger, deliberately separate piece of work (Faz 5.2), not done here.

## The CLI Closes Its Last Self-Hosting Gap, Plus Two New Ways to Inspect a Chat

Every other piece of self-hosted account/device management already had a CLI counterpart (`memo remote list-devices/add-device/revoke-device`) except accounts themselves — closed with `memo remote list-accounts/add-account/delete-account`, the same pattern, all the way down to `add-account` defaulting `--role` to `"user"` (matching the new permission system's own "nothing checked = chat only" default) and taking a comma-separated `--perm models,memory,...` list, where an unrecognized name is a hard error instead of a silently-granted-fewer-permissions-than-intended typo.

Separately: `memo -p "message"` has printed a `[chat:<id>]` line since it was added, and `-chat <id> -p "..."` already let you continue that exact conversation — but there was no way to actually look at what was *in* a chat from the terminal. Two new flags close that, deliberately scoped so they only mean anything paired with `-chat` (there's no bare `memo -list`):

- **`-chat <id> -list`** prints that chat's message history.
- **`-chat <id> -memory usage`** sums up how many memories were retrieved and injected for each message in that chat, per-message and as a total — real, already-persisted data (`MemoryUsed`, the same count the "N memories used" badge in the GUI shows), not a new measurement.
- **`-memory saved`, deliberately, does not exist as a working command.** It was the obvious next thing to build alongside `usage` — and turned out to be impossible to build honestly. Memory entries carry no record of which chat produced them at all (`SaveInteraction` never took a chat ID as a parameter, going all the way back), so "what did this specific chat save to memory" genuinely can't be answered from today's data model. Rather than silently return an empty list, or worse, every recently-saved memory regardless of which chat it actually came from, the flag exists and is refused outright with an explanation of exactly why — a wrong-but-plausible-looking answer here would have been worse than no answer at all.

## Big Feature: Kilo Code Joins the Provider List, With a Real Free/Paid Model Browser

Requested directly, with the exact bar to clear: add Kilo Code (`app.kilo.ai`) as a provider like OpenCode Zen, models fetched live from the real API — never hand-typed — and, like OpenRouter's existing model browser, free models sorted to the top and marked with a green checkmark.

Kilo's AI Gateway turned out to mirror OpenRouter's own `/models` response shape closely enough to reuse the same rich model-browser dialog verbatim, once a real backend endpoint (`/api/kilo/models`, needing no API key at all — confirmed against the live endpoint) exists to serve it: 368 real models, 18 correctly flagged free. **A real trap found by pulling the live data before writing the parser, not after:** several of Kilo's own "auto-routing" models (e.g. `kilo-auto/frontier`, which picks whichever underlying model actually handles the request) report a pricing field of `"-1"` — meaning "not a fixed price," not "free" — which a naive "prompt price is zero" heuristic would have silently misclassified as free. Kilo's response carries a direct `isFree` boolean per model instead, used as-is.

Once that landed and looked right in the app, the same question came back for **OpenCode Zen**: same free-sorted, green-checkmark treatment, but explicitly *not* for OpenCode Go, since its catalog is mostly paid. OpenCode Zen's real `/models` endpoint, unlike Kilo/OpenRouter, carries no pricing metadata at all — but free models are marked with a plain `-free` suffix on the model id itself (`deepseek-v4-flash-free`, `laguna-s-2.1-free`, ...), confirmed against the live catalog: 64 models, 8 free. (OpenCode Go, checked out of the same curiosity, turned out to have exactly one free model of its own, `ox-alpha-free`, out of 29 — not the literal zero the initial ask assumed, flagged but deliberately left out per the same "not worth it for one model" call.)

**A real live bug, and the actual lesson behind it.** Right after this shipped, clicking "Select" on Kilo Code did nothing at all — no error, no dialog, nothing. Extensive review of both the Dart and Go sides of the request path found no bug; a fresh backend build, tested by hand with the exact request the app would send, answered correctly. The actual cause: Memo attaches to an already-running backend process on its configured port instead of always starting a new one, so rebuilding only the Flutter frontend and relaunching still talks to whatever backend happened to already be running — in this case, one built before `/api/kilo/models` existed. `memo --kill` (which stops every process Memo owns and frees its ports) plus a full relaunch resolved it immediately, no code change needed. Worth knowing for anyone else hitting a change that "doesn't seem to do anything" after a rebuild: frontend and backend are separate processes here, and only one of them necessarily just got rebuilt.

## Fixed: The Provider Picker Actually Looked Broken

Once Kilo was live in the real app, three concrete problems surfaced from actually clicking through Settings → API Providers, none of which had been obvious from the code alone:

- **The "Add API provider" dropdown prefixed every row with a bare Unicode symbol** (○ ◆ ✕ ⚡ ■ ↔ △ ▸ ☁) instead of a real logo — the dialog's own header avatar already rendered real logos correctly, but the dropdown list pulled from a separate, older text-symbol helper that never got updated to match. OpenCode Zen/Go and the brand-new Kilo entry had no logo asset registered at all, falling back to a generic cloud icon regardless of what the caller actually asked for — including a small, separate, genuine bug found along the way: that generic-icon fallback hardcoded a fixed 18px size no matter what size the caller requested, so it rendered visibly smaller than a real logo sitting right next to it in the same row. Fixed by sourcing real logo assets for OpenCode and Kilo (Simple Icons and Kilo's own site favicon respectively) and giving the size-less fallback an actually-fitting icon per provider family instead of one generic cloud for everything.
- **The dropdown itself could visibly spill outside the Settings dialog's own rounded card**, with mismatched square corners, once it had thirteen real-logo rows to show and not enough room below it on a smaller window — a native dropdown menu renders in the app's top-level overlay layer, not clipped to whatever dialog it's nested inside. Replaced with a purpose-built picker matching the app's own already-established rounded-dialog pattern (the same one the model browser above uses): height capped relative to the actual screen, scrolling internally instead of overflowing, and real logos instead of glyphs in every row.
- **The Providers list itself came pre-populated with nine "Disabled" placeholder cards** — one for every known provider type — before a user had ever added anything at all, direct feedback: "burada kullanmayacağım bir modeli saçma sarak görmek istemiyorum." Fixed on both ends: a fresh install no longer seeds these placeholders in the first place, so it starts genuinely empty; and, since that alone doesn't retroactively clean up an install that already has them sitting in its saved config, the Providers list also now hides any entry that's disabled *and* has no API key *and* no custom base URL — without deleting anything from the saved file itself. Whatever the user actually configured, enabled, or entered a key for still shows; nothing pre-seeded and never touched does.

## Still Open

- Orchestra Mode's single-completion path has no tool-calling to plug the new scoped web-search mechanism into — that specific combination (Orchestra + web search + Agent Mode off) currently does no search at all.
- The live chat view can show a turn as already finished while an Orchestra task's permission request is still pending in the background (the backend itself handles this correctly; the dialog just doesn't always appear on screen while it's happening) — carried over from v3.5.5, not yet revisited.
- Reasoning-effort's fallback-to-a-different-vendor path (when the exact requested provider type isn't configured) doesn't carry an effort level — the fallback vendor's own semantics can't be inferred from the original request.
- ngrok's binary download has no real checksum pin (see H04 above) — genuine tamper-resistance against a compromised CDN would require pinning to one specific ngrok version, a deliberate trade-off not made unilaterally.
- Built-in TLS, and starting/stopping a Tailscale/ngrok tunnel from the CLI, remain not done (carried over from v3.5.5).
- Agent mode and web search are still single, global toggles for normal chat — `/agent on`/`/web on` typed into a Telegram or WhatsApp self-chat conversation flips the same setting used by ordinary chat and the other self-chat surface, not something scoped per-surface. (Self-chat itself no longer depends on this toggle for its own tool access — see the fix above — but the toggle still exists and still has this cross-surface effect on everything else that reads it.)
- The Telegram bot token (`data/telegram.json`) isn't included in Memo's export/import or Google Drive backup yet, unlike `providers.json`.
- No `telegram_send` agent tool exists yet — the agent can message WhatsApp contacts on request, but has no equivalent way to send an arbitrary Telegram message.
- Per-capability account permissions only hide tabs inside the Settings dialog so far — the top-level Model Store/Calendar/Routines screens aren't gated the same way yet (the backend still blocks their actual mutating actions regardless of whether the nav icon is visible).
- The Agent permission can't fully isolate a restricted account, because agent mode is still one flag shared by the whole backend process rather than scoped per account — real per-account isolation (Faz 5.2) is a separate, materially bigger piece of work, not started.
- `-memory saved` (the CLI flag) is refused on purpose, not a bug to fix later without a real, deliberate data-model change: memory entries have no field recording which chat produced them, and adding one is a genuine schema change, not done here.
- OpenCode Go's one free model (`ox-alpha-free`) isn't surfaced in the rich free/paid browser the way OpenCode Zen's now are — a two-line addition following the exact same pattern, deliberately skipped since a single free model out of 29 wasn't judged worth it.
